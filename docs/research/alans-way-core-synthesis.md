# Alan’s Way: core product synthesis

Research snapshot: **2026-10-27 brief; sources retrieved 2026-10-28 UTC**. Alex’s updated seven features supersede the earlier four pillars. This is a decision proposal and source review, not production certification. **UNVERIFIED** means an installed behavior, external integration or proposed result has not been demonstrated. Effort and acceptance numbers below are planning judgments, not measurements. [core-features.md:15–31][F15-31]

## One-page product definition

**Alan’s Way is a simple workspace for working alongside an existing cloud agent:** chat on the left, a capable shared browser beside it, local Mac computer use, and a visible VM that carries browser work when the laptop sleeps. It is for people who want their existing production assistant to work on their computer while they watch, steer and continue the same conversation from another device. **Hermes and Grok Bot are the targets; Claude Duet is conditional.** This is the intended product, not a claim that every part works today. [core-features.md:17–25][F17-25] [agent-compat-matrix.md:31–43][C31-43]

The seven core commitments are:

1. **Workspace:** one very simple left-side chat and a browser with the feel of ChatGPT desktop’s built-in browser. Simplicity governs the whole experience. [core-features.md:19–27][F19-27]
2. **Computer use:** extremely fast, accurate MCP/CUA on Alex’s **local Mac and inside the workspace browser**, including when a remote agent drives it. Codex computer use is the quality benchmark. [core-features.md:20–24][F20-24]
3. **Lid-close handoff:** browser work already underway locally continues on the VM; merely routing the next task there is insufficient. [handoff-ux.md:7–9](https://github.com/capthvnsen/alans-way/blob/0938511a1d94354ef18ec3850652f7810d119269/docs/research/handoff-ux.md#L7-L9)
4. **Live VM window:** retain a live, identifiable view of that VM’s desktop, with explicit watch/take-control. It remains core even when hidden. [core-features.md:22–27][F22-27] [handoff-ux.md:25–31](https://github.com/capthvnsen/alans-way/blob/0938511a1d94354ef18ec3850652f7810d119269/docs/research/handoff-ux.md#L25-L31)
5. **Same threads everywhere:** Telegram or the agent’s own app owns the conversation across devices. Browser host changes must not create another transcript or assistant. [core-features.md:188–190][F188-190]
6. **Stock production agents, added tools:** integrate supported tools/plugins/configuration without agent forks. One shared implementation serves Hermes and Grok; Duet must qualify separately. [agent-compat-matrix.md:19–29][C19-29]
7. **Proactivity:** useful initiative in the existing thread, with quiet hours, pause, backoff and consequential-action consent. Use each provider’s native scheduling owner. [proactivity-identity.md:42–50][P42-50] [proactivity-identity.md:451–465][P451-465]

**What it is not:** a replacement agent runtime, a new conversation/memory service, a general fleet orchestrator, or a promise that every live page can migrate unchanged. Voice, elaborate avatar customization and additional client targets do not lead this roadmap. Trust and human control are acceptance requirements across the seven features, not an eighth product pillar. Claude Code and Codex are deferred targets; if later justified, use only a thin CLI wrapper over Tailscale to the same tools. ## Tailscale decision

**Confirm Tailscale as the backbone for all Alan-controlled Mac↔VM and device↔VM tool, mirror and desktop-view traffic.** Keep app HTTP/CDP loopback-only behind its connector. SSH stdio, private HTTP and noVNC WebSockets are application protocols riding that backbone. Setup’s tailnet validation is stronger than generic runtime SSH/viewer validation, so configuration still needs route verification. [handoff-ux.md:33–41][H33-41] [core-features.md:192–200](https://github.com/capthvnsen/alans-way/blob/17f1b61e1ef783ae2b98647d44731a9c06c2887d/docs/research/core-features.md#L192-L200)

**Challenge “everything” as an unconditional existing fact.** Telegram and vendor app/model services retain provider networking. Grok documents Tailscale on Enterprise hosted computers, but remote URL MCP requests originate on separate connector infrastructure; joining its computer does not establish private URL reachability. **UNVERIFIED:** Alex’s account eligibility, command-connector networking, private HTTP/SSH route and persistence after recreation. [agent-compat-matrix.md:45–56][C45-56] [Grok private networks](https://docs.x.ai/grok-bot/private-networks) [Grok MCP network policy](https://docs.x.ai/grok-bot/security#mcp-servers-and-the-network-policy)

**Recommendation:** first qualify a stock Grok command connector on an authenticated tailnet member to the always-on VM; test private HTTP if SSH is blocked. Never depend on the laptop as the sole relay. If unavailable, record **Grok integration blocked under strict private-tailnet policy**. Funnel is a possible explicit exception: it exposes public HTTPS and has bandwidth limits; it does not make an off-tailnet connector private. Do not assume authorization for public ingress or open the Mac API/viewer. This research changes no exposure. [proactivity-identity.md:19–27][P19-27] [agent-compat-matrix.md:51–56][C51-56] [Tailscale Funnel](https://tailscale.com/docs/features/tailscale-funnel)

## Explicit resolutions of the research conflicts

These are synthesis recommendations for later implementation, not completed changes.

| Disagreement | Resolution and reason |

| **Are handoff and cookie transfer absent, or already seamless?** | Neither blanket claim holds. Distinguish same-host control, manual checkpoint and automatic mirror restore. Code implements the latter two; normal fresh setup and full live acceptance are unproved. Manual checkpoints omit cookies; automatic mirrors copy selected cookies. Preserve explicit reconstruction/account/uncertain-action limits. [core-features.md:35–43][F35-43] [handoff-ux.md:56–122][H56-122] [handoff-ux.md:106–122][H106-122] |

## Open questions for Alex

1. **Private ingress:** which production Grok account/plan can join the tailnet, and must support wait if its supported connector cannot reach it privately, or would you accept a narrowly authenticated Funnel exception? Default recommendation: private first. [agent-compat-matrix.md:45–56][C45-56]
2. **Left-side Grok chat:** must its actual thread render in Workspace, or is opening the same native thread an acceptable interim F1 limitation? Default recommendation: do not call an activity/deep-link pane complete without your acceptance. [core-features.md:184–190][F184-190]
3. **Transfer contract:** are selected site cookies/text drafts allowed to move automatically to the chosen VM, with visible scope and revocation? Which accounts/sites define acceptance, and should a migrated task stay on VM until completion? Default recommendation: yes to staying on VM; disclose reconstruction limits.
