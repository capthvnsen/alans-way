# Per-bot desktops on one VPS: multiple displays vs containers vs shared browser

Research date: 2026-10-06. This is a source review and architecture analysis against primary documentation (Chromium, Docker, Kasm, Guacamole, noVNC/websockify, x11docker manuals and repos) plus this repo's current code. No containers were launched, no displays provisioned, and no memory measurements were taken on a live system.

## Recommendation

Yes, this is possible at every isolation tier, and the cheapest tier covers most of the value. **Per-bot Xvfb displays with per-bot Chromium instances (no containers)** is the sensible first step: it is the existing stack repeated as more systemd units, gives each bot a separate screen, sign-in profile, and stream, and confines "Take control" to one bot. **Containers** buy real filesystem/process/network isolation and the "each bot has its own machine" story, at the cost of a Docker daemon (root-equivalent control socket) on the multi-bot host and the Chromium-sandbox-in-container problem. **Per-bot browsers on today's single shared display** is the smallest change but keeps the weakest isolation: same X server means bots can snoop each other's windows/input at the X protocol level.

On RAM: the user's intuition is right that RAM is the binding constraint, but the dominant term is the browser, not the desktop or the container. Measured Chromium figures put the browser process at ~100MB plus ~50–230MB per renderer/tab; Xvfb's framebuffer is a few MB and x11vnc/websockify are small daemons. So the three options for 4 bots differ by roughly the display stack (tens–low-hundreds of MB per bot) plus a small per-container shim — containers add maybe 0.5–1GB total over bare displays, not a VM worth of RAM each. **4 bots fits comfortably on an 8GB VPS, is tight on 4GB**; Kasm's own default reservation of 2768MB + 2 cores per full-desktop session is the published conservative bound, and a minimal Xvfb+WM+Chromium container is well under that. A cap of ~4 is reasonable on 8GB with per-instance cgroup limits and swap.

## Options, cheapest to strongest isolation

**N× bare displays (no containers).** Run Xvfb on :99…:102, each with its own x11vnc, websockify/noVNC port, and `chromium --user-data-dir=<per-bot>` — the same units the project already documents (`desktop/docs/vps-browser.md:63-100`), parameterized by display. Two facts make this the natural increment: two running Chromium instances cannot share a user data directory, and one instance cannot span multiple X displays, so per-display implies per-instance anyway ([Chromium user data dir docs](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/user_data_dir.md)). Caveat: X isolation is display-level only. Clients on *different* X servers can't snoop each other, but all displays still run as the same Unix user sharing a filesystem, `~/.Xauthority`, and process table — the x11docker project documents why shared-X access leaks (keylogging, remote control) and runs a second X server precisely to avoid them ([x11docker README](https://github.com/mviereck/x11docker)).

**Containers.** Mature, maintained options exist: [KasmVNC](https://github.com/kasmtech/KasmVNC) merges the X server and VNC server into one `Xvnc` process ([Xvnc man page](https://kasmweb.com/kasmvnc/docs/master/man/Xvnc.html)); [kasmtech/workspaces-images](https://github.com/kasmtech/workspaces-images) desktop/application images run standalone (`docker run --shm-size=512m -p 6901:6901 kasmweb/<image>`) without the full Workspaces platform; [linuxserver/webtop](https://github.com/linuxserver/docker-webtop) ships full desktop images streamed to the browser (now on the Selkies base, HTTPS on :3001); [jlesage/docker-baseimage-gui](https://github.com/jlesage/docker-baseimage-gui) is a minimal, actively maintained X-app base (releases through 2025). Versus bare displays, each container adds a private filesystem, PID table, `/tmp`, and network namespace — plus a genuinely separate browser profile/sign-in per bot — while still sharing the host kernel ([Docker overview](https://docs.docker.com/get-started/docker-overview/)). No GPU is needed: Xvfb is already a software framebuffer ([Xvfb(1)](https://www.x.org/releases/X11R7.7/doc/man/man1/Xvfb.1.xhtml)).

## The RAM question, quantified

- **Chromium dominates.** Its multi-process model gives every instance a browser process plus one renderer per site/tab — "5–7 chrome.exe processes" in typical browsing ([Chromium memory backgrounder](https://chromium.googlesource.com/playground/chromium-org-site/+/refs/heads/main/developers/memory-usage-backgrounder/index.md), [multi-process architecture](https://www.chromium.org/developers/design-documents/multi-process-architecture/)). A measured breakdown (Chrome 70 era): browser process ~103MB nearly constant, each renderer ~53–231MB per page, 334MB total for one YouTube tab ([ACM 10.1145/3358695.3360915](https://dl.acm.org/doi/fullHtml/10.1145/3358695.3360915)). Each `--user-data-dir` instance is a fully separate process tree — nothing is shared between instances. Budget **~0.5–1.5GB per bot browser** depending on tab count; the current global cap of 40 VPS tabs (`desktop/scripts/browser-mcp.cjs:76`) is the other dial.
- **Display stack is small.** Xvfb "emulates a dumb framebuffer using virtual memory" — a 1280×1024×32 framebuffer is ~5MB; the server plus x11vnc plus websockify are tens of MB total per display (estimate from architecture, not measurement; [Xvfb(1)](https://www.x.org/releases/X11R7.7/doc/man/man1/Xvfb.1.xhtml)). KasmVNC collapses X+VNC to one process, cutting per-display overhead further.
- **Container overhead is small.** Containers are namespaced processes sharing the host kernel, not VMs ([Docker overview](https://docs.docker.com/get-started/docker-overview/)); per container you pay the runtime shim plus whatever runs inside — i.e., the display stack repeated. Shared image layers keep page cache common across bots.
- **Envelope for 4 bots:** today (1 browser, 4 bot-ids) ≈ 0.5–1.5GB Chromium + ~0.2GB stack → fine on 4GB. Four browsers on four displays ≈ 2–6GB + ~0.4–0.8GB → **8GB realistic, 4GB marginal**. Four containers adds a small per-container shim on top — call it +0.2–0.5GB — so same 8GB answer. Kasm publishes 2768MB + 2 cores as the *default reservation* per session and documents oversubscription of both ([system requirements](https://kasm.com/docs/latest/install/system_requirements.html), [sizing guide](https://kasm.com/docs/latest/how_to/sizing_operations.html)) — their images include a full DE, so a minimal stack lands lower.
- **Enforcement exists at both tiers:** `docker run --memory=` hard-limits a container ([Docker resource constraints](https://docs.docker.com/engine/containers/resource_constraints/)); `MemoryMax=` does the same for a systemd unit ([systemd.resource-control](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html)). Kasm recommends swap on agents for stability ([system requirements](https://kasm.com/docs/latest/install/system_requirements.html)).

## Container-specific gotchas

- **Chromium's sandbox vs Docker's default profile.** Chromium's renderer sandbox needs `clone`/`unshare` with namespace flags; Docker's default seccomp profile denies namespace-cloning calls **except** `CLONE_NEWUSER` ([Docker seccomp docs](https://docs.docker.com/engine/security/seccomp)), so on many host kernels the sandbox still works. On Ubuntu 23.10+ hosts, AppArmor additionally restricts unprivileged user namespaces for unconfined binaries ([Chromium docs](https://chromium.googlesource.com/chromium/src/+/main/docs/security/apparmor-userns-restrictions.md)); the setuid sandbox helper is the documented alternative. Grafana's crocochrome documents the actual three-way tradeoff: `seccomp=unconfined`, `--no-sandbox`, or a custom profile ([chromium-sandbox.md](https://github.com/grafana/crocochrome/blob/main/doc/chromium-sandbox.md)). `--no-sandbox` "should never be used when browsing the open web" — which is exactly what bots do. This project currently prefers the sandbox on (`desktop/docs/vps-browser.md:49`), so plan for the setuid helper or a custom seccomp profile, not the easy flag.
- **The daemon is root.** Anyone able to talk to `docker.sock` can mount the host filesystem into a container — Docker's own docs call this out, and bots with shell access on the host are exactly who you don't want holding it ([Docker daemon attack surface](https://docs.docker.com/engine/security)). Mitigate with [rootless Docker](https://docs.docker.com/engine/security/rootless) or daemonless rootless Podman.
- **`/dev/shm`.** Chromium in containers needs a larger shared-memory segment than Docker's default; both Kasm (`--shm-size=512m`) and webtop (`shm_size: "1gb"`) ship that in their run examples ([workspaces-images](https://github.com/kasmtech/workspaces-images), [docker-webtop](https://github.com/linuxserver/docker-webtop)).

## Impact on this app and architecture

- **Viewer:** the app embeds exactly one URL — `prefs.remoteUrl` is a single string (`desktop/src/main.cjs:78,592`) feeding one `RFB` instance (`desktop/src/remote.js:26`). N streams means either N configured URLs switched by bot selection, one websockify port with token-based target selection (`--token-plugin` maps the client's `token` parameter to a target — [websockify README](https://github.com/novnc/websockify)), or a real gateway like Apache Guacamole, which proxies N VNC connections through guacd to an HTML5 client ([Guacamole architecture](https://guacamole.apache.org/doc/gug/guacamole-architecture.html)). The token-plugin route is the smallest delta: one port, per-display targets.
- **Broker/connectors:** per-bot desktops want per-bot brokers — each writes its own `connection.json` under `HERMES_VPS_BROWSER_DATA` (`desktop/scripts/vps-browser-host.cjs:13-20`). Each Hermes profile's connector already takes `--connection <path>` (`desktop/scripts/browser-mcp.cjs:41-44`), so routing is a config delta, not a rewrite — with containers, publish each broker's loopback port or run the connector inside. One wrinkle: the Mac app holds a *single* `vpsBrowser` `{sshHost, scriptPath}` pref and the SSH `request` path reads one default connection file (`desktop/src/vps-browser.cjs:5-14`, `main.cjs:586-589`), so a thin bot-id→broker router or per-bot data-dir selection would be needed there.
- **Take control** currently forwards input to the whole shared desktop (`remote.js:27,46`: `rfb.viewOnly = !remoteControl`). With per-bot desktops the same code scopes control to one bot — arguably a security improvement, since the human can no longer accidentally type into another bot's window.
- **Sign-ins:** today's model is one shared profile → shared logins for all bots (`docs/agent-setup.md:27-29`, `desktop/docs/vps-browser.md:7`). Per-bot browsers invert that: real isolation of cookies/credentials per bot, at the cost of signing in once *per bot*. For the "watch any bot work on logged-in sites" expectation, the human logs into the same sites four times — annoying but arguably healthier than one shared cookie jar all bots can reach.
- **Placement:** two levels — (a) containerize just the display+browser+broker, leaving Hermes gateways on the host (smaller delta, connector already reaches in via a published port); (b) full "bot machine" containers holding gateway+profile+browser. (b) matches the user's phrasing but moves gateway lifecycle, plugin installs, and SSH transports inside the image — a substantially larger change to `setup.sh` and the fleet model.

## Existing art

[Kasm Workspaces](https://github.com/kasmtech/workspaces-images) is exactly this product — containerized desktop infrastructure, one disposable container per user session streamed over KasmVNC — and linuxserver's webtop/SealShip line covers the same space ([docker-webtop](https://github.com/linuxserver/docker-webtop)). Apache Guacamole already solves "many VNC streams behind one HTML5 gateway" ([intro](https://guacamole.apache.org/doc/gug/introduction.html)). What none of them provide is this project's actual differentiator — bot-id-keyed tab ownership, per-tab agent cursors, and the connector protocol — so the sensible adoption is borrowing their *packaging* (KasmVNC or webtop-style images, possibly a Guacamole or token-plugin front end) rather than their platform.

## Evidence limits

Verified against primary sources: Kasm's published per-session requirements and sizing table; Docker's seccomp, daemon-surface, rootless, and memory-limit semantics; Chromium's process model, user-data-dir exclusivity, and sandbox requirements; Xvfb/x11vnc/websockify mechanics; this repo's single-URL viewer and broker layout. **Not verified:** any live memory measurement — the ~103MB/53–231MB Chromium figures are from a 2019-era measurement paper and will be higher on current versions; the tens-of-MB display-stack figure is architectural arithmetic, not `ps` output; Chromium-sandbox behavior inside Docker varies with host kernel and distro AppArmor defaults (Ubuntu 23.10+ specifically); Kasm's 2768MB default covers a full DE image, so a minimal bot container should land lower but that gap is unmeasured. Treat every MB figure here as a budgeting bound, not a benchmark.
