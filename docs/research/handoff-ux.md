## Finding

The browser and left chat pane already share one desktop shell, but “handoff” describes three different operations: control of a live tab, a manual cross-host page checkpoint, and outage-triggered mirror restoration. They preserve different state and have different safety gates. A seamless full browser/session migration on lid close is **UNVERIFIED**; the inspected implementation reconstructs selected page state after an outage rather than moving a running Chromium session. [desktop/src/main.cjs:292–330](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/src/main.cjs#L292-L330), [desktop/src/main.cjs:2617–2647](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/src/main.cjs#L2617-L2647), [alans-way/scripts/workspace-router.cjs:1553–1587](https://github.com/capthvnsen/alans-way-agents/blob/4da7c64bcf11fec0c10c1cddc569ec125a93a032/alans-way/scripts/workspace-router.cjs#L1553-L1587)

**Recommendation:** keep the simple browser-plus-left-chat experience, make local browser work survive lid close under one logical task/tab, and show an honest readiness state. A VM-resident task can avoid repeated migrations once moved, but starting every task on the VM would not satisfy the requirement to hand off work begun in the local workspace browser. This is a product proposal, not a request for a new agent framework. [desktop/src/browser-page.cjs:1173–1207](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/src/browser-page.cjs#L1173-L1207), [desktop/scripts/vps-browser-host.cjs:743–805](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/scripts/vps-browser-host.cjs#L743-L805)

### Tailscale: confirm the backbone, challenge “everything” literally

**Confirm:** Tailscale should remain the Mac↔VM and user-device↔VM backbone, carrying restricted SSH/MCP, mirror traffic and the live VM desktop. The README requires Tailscale; Mac setup validates tailnet addresses and restricts the VM SSH key's source ranges. Keep the app API on loopback behind that route. [README.md:15–24](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/README.md#L15-L24), [scripts/connect-mac.sh:46–103](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/scripts/connect-mac.sh#L46-L103), [desktop/docs/integration.md:9–11](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/docs/integration.md#L9-L11)

**Challenge:** that is not proof that every configured connection uses the tailnet. The generic SSH validator checks syntax, while the viewer URL validator allows arbitrary HTTP(S)/WS(S) hosts. Setup enforces a stronger rule than these generic runtime validators; deployed routing needs verification. [desktop/src/core.cjs:136–170](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/src/core.cjs#L136-L170) Telegram itself is loaded from its provider, and native Hermes uses a separately configured HTTP/WebSocket endpoint. Provider chat/model traffic cannot honestly be described as entirely inside an Alan's Way tailnet. [desktop/src/main.cjs:102–103](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/src/main.cjs#L102-L103), [desktop/src/hermes-remote.cjs:1–18](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/src/hermes-remote.cjs#L1-L18)

Grok's official docs distinguish command tools on its hosted computer from remote MCP calls originating on the provider's connector servers. Joining the computer to Tailscale does not establish that those separate connector servers can reach a private tailnet URL. The current desktop guide also records blocked outbound SSH for Grok. **UNVERIFIED:** the actual Grok account can use a stock command connector over private Tailscale while Alex's Mac sleeps. [Grok network-policy/MCP documentation](https://docs.x.ai/grok-bot/security#mcp-servers-and-the-network-policy), [desktop/docs/remote-agents.md:14–22](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/docs/remote-agents.md#L14-L22)

**Proposal:** qualify a private tailnet command connector first, with the router on the always-on VM. Tailscale Serve is private-tailnet sharing; Funnel makes a service accessible from the public internet. Funnel may be an explicit Tailscale-powered ingress choice, but it cannot silently satisfy a private-only transport requirement. Do not change exposure as part of this research. [Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve), [Tailscale Funnel](https://tailscale.com/docs/features/tailscale-funnel) This ingress decision and client support belong to the compatibility report; they are a launch dependency for the same handoff UX, not a reason to fork an agent.

## 2. End-to-end paths

### A. Control handoff on the same host

Human/agent control uses tab ownership and an epoch; takeover and return invalidate older action epochs. The same live page stays on its original execution host, preserving its in-memory state. A VM agent driving a local tab still depends on the laptop being awake. This is collaboration, not cross-host session migration. [desktop/docs/integration.md:69–85](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/docs/integration.md#L69-L85), [desktop/docs/integration.md:150–163](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/docs/integration.md#L150-L163)

### B. Manual “Move to VM” and “Move back”

1. The renderer offers Move only when the VM broker is connected and the selected eligible local tab is agent-controlled, or is a retired source that can be moved back. The UI sets a busy flag and sends `handoff` with `includeDrafts:true`. Thus the backend's default of drafts-off is **not** the shipped button behavior. [desktop/src/renderer.js:470–481](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/src/renderer.js#L470-L481), [desktop/src/renderer.js:2053–2063](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/src/renderer.js#L2053-L2063), [desktop/src/main.cjs:2617–2626](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/src/main.cjs#L2617-L2626)
2. Main changes the source to human control and drains its queue, captures URL/title/scroll and matching text fields, then creates a human-controlled destination page. The VM leg uses SSH requests to the broker; the return leg creates a new local tab and waits in 100 ms steps for up to approximately 10 seconds before restoring. [desktop/src/main.cjs:2617–2637](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/src/main.cjs#L2617-L2637)
3. Restore requires the exact URL and matching field shape. It reports draft counts and `ready`/`review_required`; it does **not** establish equivalent login or business state. The source gets a retired handoff record, the destination stays human-controlled, and the VM page is activated in the desktop viewer. [desktop/src/browser-page.cjs:1193–1207](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/src/browser-page.cjs#L1193-L1207), [desktop/src/main.cjs:2639–2647](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/src/main.cjs#L2639-L2647), [desktop/scripts/vps-browser-host.cjs:1146–1165](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/scripts/vps-browser-host.cjs#L1146-L1165)
4. The retired local source is the UI route back: Move back checkpoints the **current VM page** into another new local page. It is another reconstruction, not attachment to the original live tab. The integration fixture explicitly expects different JS memory after the return. [desktop/src/renderer.js:470–481](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/src/renderer.js#L470-L481), [desktop/src/renderer.js:2053–2063](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/src/renderer.js#L2053-L2063), [desktop/test/cross-host-electron.cjs:128–146](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/test/cross-host-electron.cjs#L128-L146)

**Fragility:** source control changes happen before destination creation/restore. The helper has no encompassing rollback; a destination failure can leave the source paused, and a VM restore failure after creation can leave a partial destination. This is a static-code inference, not a reproduced deployed failure. VM source retirement failure is recorded as `sourceRetired:false`, while activation happens after saving the record into in-memory state. UX needs an explicit partial outcome and a safe resume-source action. [desktop/src/main.cjs:2624–2647](https://github.com/capthvnsen/alans-way/blob/7e05d521c2a2f9add46423e39a4b27d6e67049e3/desktop/src/main.cjs#L2624-L2647)

### C. Lid close / computer unavailable: background mirror plus router fallback

```text
While awake:
  Local agent tab → bounded page checkpoint + selected cookies
    → app SSH request helper → VM loopback broker → private mirror.json

When local execution is unavailable:
  Agent MCP client → VM workspace-router
    → detect dead local connector / failed probe / watcher offline
    → VM POST /v1/restore → set cookies → reopen pages → restore drafts/scroll
    → destination IDs + verification → VM browser connector → agent

Separately:
  Desktop chat pane → Telegram or Hermes backend
  Desktop VM viewer → WebSocket/noVNC desktop stream
```

The data and control paths above are implemented separately in the mirror collector, SSH helper, broker and router. Do not count a progress label as recovered execution. Existing restore load waits, 25-second continuation cap and 45–100-second failure deadlines are the baseline reasons to measure each stage. | Metric | Proposed target and precise definition |
| --- | --- |
| Readiness visibility | Within 1 second of a task/host state transition, update desktop status when connected; report checkpoint age from broker acknowledgements. No “ready” without an acknowledgement. |
| Pre-sleep recovery-point age | p95 ≤2 seconds, p99 ≤5 seconds for the active eligible local task while transport is healthy. Show degraded readiness beyond 5 seconds; never silently substitute an older captured page as current. |
| Already VM-hosted task | Zero browser restart/navigation caused by laptop sleep; task's next scheduled useful operation continues without waiting for laptop wake. Record server-side operation timestamps across the outage. |

| Failure detection / bounded outcome | p95 ≤3 seconds from physical loss to router detection in a controlled test. By 15 seconds from detection, show either verified continuation, explicit needs-you, uncertain action, or paused failure. Test an app hang independently from a dead SSH link. |
| Wake→view | p95 ≤2 seconds from network availability to current task status, ≤3 seconds to first live VM frame on a warm connection. Do not include human credential entry in automatic recovery latency. |
| Reliability | ≥99.5% automatic continuation of **eligible** one-tab checkpoint fixtures across at least 1,000 transitions per supported platform/transport. | Multi-tab / cold startup | Publish separate p50/p95/p99 for 1, 4 and 20 tabs and for stopped-broker/browser startup. Do not claim the warm SLA covers cold startup until measurements establish it. |

## Open questions for Alex

1. Is a task that has moved to the VM allowed to keep running there after wake, while local browser tasks still begin locally and must migrate on lid close? Recommended: yes, until a verified return is requested.
2. On wake, should the app keep watching the VM until the task ends, or offer an explicit move immediately? Recommended: watch immediately, move only on request or a verified boundary.
3. Is automatic transfer of eligible text drafts and site cookies the desired default, with a clear per-task explanation and revocation control? The current mirror already transfers both; the manual move and documentation describe different semantics.
4. Which sites/accounts and production Hermes/Grok versions define beta acceptance, and must remote tool ingress be private-tailnet-only? If a hosted Grok URL connector cannot join the tailnet, decide whether an explicitly authenticated Funnel endpoint is acceptable.
5. Must the identical Grok thread be rendered inside the workspace left pane, or is opening that same thread in Grok's own app sufficient? MCP connectivity alone does not establish a supported embedding interface.

These are product decisions; underlying current behavior and limits are documented above. No answer was assumed to authorize code changes or deployment.
